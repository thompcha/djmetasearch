# Architecture

The app supplies `ui/app.html` at the intercepted URL `https://djpoolrecords.com/__djmetasearch__/`. The document is local, but its browser origin is DJPoolRecords. This allows authenticated same-origin DJPoolRecords requests without embedding or showing the remote homepage. RVRemix search runs through the Python-side public client in `djmetasearch/rvremix.py` and its controlled result model is merged into the same UI.

`standalone_app.py` owns the Playwright context, download staging, session persistence, and authentication lifecycle. The UI requests both providers asynchronously through local bindings. The main loop sends DJPoolRecords queries to `/wp-json/dpr-search/v1/files` with the authenticated browser request context and current REST nonce; this also avoids the endpoint's rejection of requests whose referrer is the synthetic app page. `djmetasearch/results.py` creates controlled provider models from the REST `hits`, rejects untrusted URLs, excludes video entries, and labels each row before merging. A local relevance gate requires every meaningful query token in the visible DJPoolRecords name while ignoring case, punctuation, and diacritics.

RVRemix searches run in a single-worker `ThreadPoolExecutor`, outside Playwright's synchronous binding callback. Provider bindings return request IDs immediately. The main loop fetches one 50-row DJPoolRecords page per iteration and delivers the first page to resolve the UI promise; subsequent pages update the cached query model asynchronously. Paging stops when `hasMore` is false, the endpoint returns no rows, or a page contributes no new name-plus-filesize identities. RVRemix is merged whenever it finishes. A monotonically increasing search generation prevents late provider responses from replacing a newer query while still allowing cached in-flight queries to be reused.

The UI memoizes raw provider promises by a whitespace-normalized, case-insensitive query key. A modifier search exposes its already-started bare request to a subsequent **Clear** action. The cleared generation can render the shared bare DJPoolRecords model and await the shared bare RVRemix model, while the superseded modifier generation remains unable to render. Launch queries are bare by default; modifiers such as `intro` are opt-in.

Completed downloads remain in Playwright's temporary staging area while `djmetasearch/cleanup.py` works on a same-filesystem copy. MP3 ID3 and M4A Artist/Title tags are cleaned with Mutagen, saved, and used to build the final filename. The working copy is atomically moved into the download directory, then a valid embedded release year is written as the numerical Finder comment through Finder's AppleScript API and verified by immediate read-back. If any cleanup or Finder verification step fails, the placed working copy is removed and a fresh copy of the untouched staged bytes is atomically placed under the original suggested filename instead. Unsupported formats follow that unchanged placement path.

Preview media is held in a session-scoped local cache and served to the native HTML player through the intercepted media route. After a preview is ready, its pane-level Download button sends the preview request identifier back to Python. Python resolves that identifier to the cached file and copies it through the same transactional cleanup and final-placement pipeline, so this action makes no second media request and does not disturb ongoing playback. Downloads initiated from result tiles continue to use the server download URL.

Preview requests cross a Python binding and are fetched with the authenticated browser context into a session-only temporary cache. The app serves cached files from a synthetic same-origin media URL with HTTP byte-range support, allowing Chromium's native `<audio>` or `<video>` player to seek and play without sending its own remote authenticated request. Preview files are deduplicated by source URL and deleted when the app exits.

Preview source validation is intentionally narrower than general browsing: it accepts DJPoolRecords and RVRemix AJAX media actions plus signed media URLs on Dropbox's `*.dl.dropboxusercontent.com` CDN. RVRemix result downloads cross a Python binding, reuse/cache the verified audio stream bytes, and enter the same cleanup pipeline without browser navigation. DJPoolRecords download actions remain restricted to its own host.

The RVRemix client reads the current top Search module token and nonce from `/audio/`, converts `Artist - Title` to `"Artist" "Title"`, and retries one bootstrap if the widget metadata expires. It retains only audio MIME types/extensions and deduplicates repeated Box entries by normalized filename. A final local relevance gate requires the meaningful artist and title tokens in the visible filename. Token comparison ignores case, diacritics, punctuation, and common connector words, with a compact alphanumeric fallback for joined/separated forms such as `AC/DC` and `ACDC`.

The DJPoolRecords REST endpoint uses the browser's WordPress session and an `X-WP-Nonce` value exposed by the authenticated homepage. The versioned bootstrap cache stores only that nonce and the validated endpoint URL. A rejected search queues one session refresh. The launcher opens the homepage in a background tab, checks for the authenticated `Search audio files...` control, and reads the current configuration. A login/challenge tab is brought forward only when that control is unavailable. Credentials are read into memory from environment variables or the macOS Keychain and submitted without being persisted by the standalone app. The rendered homepage state and audio-search presence are authoritative during recovery: a leftover `wordpress_logged_in_*` cookie alone is not treated as proof of authentication. After login, the helper reloads the homepage, confirms the audio search, and resumes the queued query.

Runtime state and results are deliberately separate: browser/session metadata is persisted and ignored by Git; queries, parsed results, and raw responses stay in memory.
