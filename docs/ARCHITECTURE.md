# Architecture

The app supplies `ui/app.html` at the intercepted URL `https://djpoolrecords.com/__djmetasearch__/`. The document is local, but its browser origin is DJPoolRecords. This allows authenticated same-origin DJPoolRecords requests without embedding or showing the remote homepage. RVRemix search runs through the Python-side public client in `djmetasearch/rvremix.py`; DJFolders search runs through the authenticated Python client in `djmetasearch/crate_search.py`. Their controlled result models are merged into the same UI.

`standalone_app.py` owns the Playwright context, download staging, session persistence, and authentication lifecycle. The UI requests all providers asynchronously through local bindings. The main loop sends DJPoolRecords queries to `/wp-json/dpr-search/v1/files` with the authenticated browser request context and current REST nonce; this also avoids the endpoint's rejection of requests whose referrer is the synthetic app page. `djmetasearch/results.py` creates controlled provider models from the REST `hits`, rejects untrusted URLs, excludes video entries, and labels each row before merging. A local relevance gate requires every meaningful query token in the visible DJPoolRecords name while ignoring case, punctuation, and diacritics. Sorting puts otherwise-vanilla copies containing configured preferred labels at the top, followed by other vanilla Intro/Outro/Clean/Dirty copies, then unlabelled plain/original copies, then named Intro remixes/edits and other variants. Promoted results are sorted and clustered by a normalized core label; trailing delivery descriptions such as `Squeaky Clean`, `Clean`, `Dirty`, and `Explicit` are ignored, keeping all `CK Intro` copies adjacent. Punctuation and connector wording inside delivery-only labels do not matter, so `Intro Outro`, `Intro - Outro`, and `Intro and Outro` remain vanilla; a label containing a named edit/remix does not. A preferred label on a named edit/remix does not normally promote it: it remains beside the other delivery copies in that named version family. TMU-branded versions are the explicit exception when both the artist is vanilla and the version label itself starts with TMU, such as `TMU Intro Edit`; `Vs` artists and mashup source lists are excluded. A separate TMU copy tag on another named version also does not promote that family. Named families are stably clustered after ignoring provider numbering, punctuation, BPM, delivery qualifiers such as Clean, Dirty, CK Cut, and Break Fill, and minor provider wording differences around a recognized version label.

RVRemix and DJFolders searches run in background executors, outside Playwright's synchronous binding callbacks. Provider bindings return request IDs immediately. The main loop fetches one 50-row DJPoolRecords page per iteration and delivers the first page to resolve the UI promise; subsequent pages update the cached query model asynchronously. Paging stops when `hasMore` is false, the endpoint returns no rows, or a page contributes no new name-plus-filesize identities. Each background provider is merged whenever it finishes. A monotonically increasing search generation prevents late provider responses from replacing a newer query while still allowing cached in-flight queries to be reused.

DJFolders requests use `X-API-Key` from `DJFOLDERS_API_KEY` or the macOS Keychain service `djfolders` (with legacy Crate Search names accepted for compatibility). When neither exists on macOS, a native hidden-entry dialog accepts the shared key, checks the health endpoint, and stores it in Keychain before the browser launches; cancellation leaves the provider disabled and prompts again on the next launch. The key is never stored in source or initial search-result models. Searches request only audio and page in 500-row increments; filename relevance is rechecked locally so matches caused only by folder names are omitted. Results are initially unresolved. Preview or Download resolves only the selected string track ID, validates the returned host, path, action, and ID, and then uses the signed media URL. Direct audio playback preserves the service's HTTP Range behavior; downloads pass through the normal managed cleanup pipeline.

The UI memoizes raw provider promises by a whitespace-normalized, case-insensitive query key. A modifier search exposes its already-started bare request to a subsequent **Clear** action. The cleared generation can render the shared bare DJPoolRecords model and await the shared bare RVRemix model, while the superseded modifier generation remains unable to render. Launch queries are bare by default; modifiers such as `intro` are opt-in.

Modifier filtering uses whole words. The **Trans** modifier accepts both `trans` and `transition`/`transitions`, allowing the short provider query to be supplemented by transition-labelled rows from the asynchronously paged bare results.

Results with a known provider-reported size below 1 MiB are discarded both while parsing provider responses and again during asynchronous model merging. Results at exactly 1 MiB and results without a parseable size remain visible.

A plausible terminal BPM from 40 through 250 is retained as structured result metadata while being removed only from the UI display name; the original remote name and download filename remain unchanged. The BPM and Size columns sort numerically in either direction, keep equal values stable, and leave unknown values at the bottom. Activating either column replaces the other column's active sort.

Completed downloads remain in Playwright's temporary staging area while `djmetasearch/cleanup.py` works on a same-filesystem copy. MP3 ID3 and M4A Artist/Title tags are cleaned with Mutagen, saved, and used to build the final filename. The working copy is atomically moved into the download directory, then a valid embedded release year is written as the numerical Finder comment through Finder's AppleScript API and verified by immediate read-back. If any cleanup or Finder verification step fails, the placed working copy is removed and a fresh copy of the untouched staged bytes is atomically placed under the original suggested filename instead. Unsupported formats follow that unchanged placement path.

Preview media is held in a session-scoped local cache and served to the native HTML player through the intercepted media route. After a preview is ready, its pane-level Download button sends the preview request identifier back to Python. Python resolves that identifier to the cached file and copies it through the same transactional cleanup and final-placement pipeline, so this action makes no second media request and does not disturb ongoing playback. Downloads initiated from result tiles continue to use the server download URL.

Preview requests cross a Python binding and are fetched with the authenticated browser context into a session-only temporary cache. The app serves cached files from a synthetic same-origin media URL with HTTP byte-range support, allowing Chromium's native `<audio>` or `<video>` player to seek and play without sending its own remote authenticated request. Preview files are deduplicated by source URL and deleted when the app exits.

Preview source validation is intentionally narrower than general browsing: it accepts DJPoolRecords and RVRemix AJAX media actions, exact signed DJFolders media actions, and signed media URLs on Dropbox's `*.dl.dropboxusercontent.com` CDN. RVRemix and DJFolders result downloads cross a Python binding, reuse/cache verified audio bytes, and enter the same cleanup pipeline without browser navigation. DJPoolRecords download actions remain restricted to its own host.

The RVRemix client reads the current top Search module token and nonce from `/audio/`, converts `Artist - Title` to `"Artist" "Title"`, and retries one bootstrap if the widget metadata expires. It retains only audio MIME types/extensions and deduplicates repeated Box entries by normalized filename. A final local relevance gate requires the meaningful artist and title tokens in the visible filename. Token comparison ignores case, diacritics, punctuation, and common connector words, with a compact alphanumeric fallback for joined/separated forms such as `AC/DC` and `ACDC`.

The DJPoolRecords REST endpoint uses the browser's WordPress session and an `X-WP-Nonce` value exposed by the authenticated homepage. The versioned bootstrap cache stores only that nonce and the validated endpoint URL. A rejected search queues one session refresh. The launcher opens the homepage in a background tab, checks for the authenticated `Search audio files...` control, and reads the current configuration. A login/challenge tab is brought forward only when that control is unavailable. Credentials are read into memory from environment variables or the macOS Keychain and submitted without being persisted by the standalone app. The rendered homepage state and audio-search presence are authoritative during recovery: a leftover `wordpress_logged_in_*` cookie alone is not treated as proof of authentication. After login, the helper reloads the homepage, confirms the audio search, and resumes the queued query.

Runtime state and results are deliberately separate: browser/session metadata is persisted and ignored by Git; queries, parsed results, and raw responses stay in memory.
